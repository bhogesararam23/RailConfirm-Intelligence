# Inference and group probability behavior

Status: modelling and serving specification, not a trained-model claim.

## Inference contract

The service receives a validated journey context and per-passenger original/current statuses, each with source/time metadata when available. It returns either:
- a supported probability distribution for a named target; or
- a structured abstention/unavailable result with a stable reason code.

No value may be generated by an LLM or UI as a replacement for model output.

## Processing steps

1. Validate required input fields and timestamp semantics.
2. Normalize recognized statuses and preserve their raw strings.
3. Resolve class, quota, route segment and prediction horizon where known.
4. Compute the feature snapshot as of `prediction_at`.
5. Check supported category/feature coverage and data freshness.
6. Resolve an approved model version compatible with the feature schema and target.
7. Generate raw model scores.
8. Apply the calibration method selected on validation data.
9. Validate finite outputs, class support, bounds and sum-to-one tolerance.
10. Compute group events from a supported joint/structured distribution.
11. Attach provenance, version, uncertainty and limitation metadata.
12. Return results or abstain.

## Probability output

For an exhaustive, mutually exclusive outcome set, each passenger's probabilities must lie in [0, 1] and sum to 1 within a documented numerical tolerance. If CNF/RAC/WL are not exhaustive for the selected population, include OTHER or state precisely that the probabilities are conditional on a restricted target population. Do not hide this condition.

Do not present decimal precision beyond what model quality and evidence support. Percentage rounding belongs to the presentation layer; machine-readable probabilities should retain enough precision for calculation.

## Group events

For a group with final outcomes (Y_1,…,Y_n), group events include:
- all passengers CNF;
- all passengers CNF or RAC;
- exactly (k) passengers CNF;
- at least (k) passengers CNF;
- one or more passengers WL;
- specific group combinations when product value and evidence justify them.

The primary ideal is a calibrated joint distribution over passenger outcomes. Alternatives such as conditional sampling or a structured latent group model may be evaluated. A simple independence product can be implemented as a baseline for comparison, but must be labelled as an assumption-driven baseline and cannot quietly become the primary method.

## Why marginal probabilities are insufficient

Knowing each passenger's chance of CNF does not uniquely determine the probability that everyone is CNF. Different dependence structures can have identical passenger marginal probabilities but different all-confirmed probabilities. If the model cannot estimate that dependence, it must say that the group estimate is unavailable or clearly mark an explicitly evaluated approximation.

## Calibration

- Fit calibration on a validation period only.
- Preserve the class order and target definition during calibration.
- Evaluate calibration separately on a locked future period.
- Check class-wise and segment calibration when sample size permits.
- Recalibrate only using a documented process and new training/evaluation versions.
- Do not turn model confidence or entropy into a probability without evidence.

## Abstention reasons

`AbstentionReason` in `backend/railconfirm/domain/prediction.py` is the public, versioned vocabulary. The codes below are the ones the implementation actually emits; a reason is added only with a producer, a test and a frontend message.

| Code | Emitted when | Distinct from |
|---|---|---|
| `unknown_status` | The raw status string has no verified mapping. | `unsupported_status` — the code was recognised as not-a-status. |
| `unsupported_status` | The status is known but sits outside the target population (cancelled, censored, other). | `unknown_status` — here the meaning is known and the request is out of scope. |
| `unsupported_class` | No model or approved cohort covers the journey class. | `insufficient_sample` |
| `unsupported_quota` | No model or approved cohort covers the quota. | `insufficient_sample` |
| `no_trained_model` | No trained model artifact is active in the registry. | `no_approved_data` |
| `no_approved_data` | No dataset approved for estimation is available, so there is no evidence base at all. This is the current repository state. | `no_trained_model` — a model can exist without approved data and approved data can exist without a model. |
| `insufficient_sample` | A cohort exists but holds fewer records than the configured minimum. | `no_approved_data` |
| `invalid_input` | The request cannot be represented as a valid domain object. | API-layer validation errors |

`no_trained_model` and `no_approved_data` are deliberately separate because they call for different work: training a model versus clearing a dataset through `docs/data/DATASET_INTAKE_CHECKLIST.md`. Collapsing them would hide which gate is actually open.

Codes once proposed for this document (`DATA_TOO_STALE`, `FEATURE_SCHEMA_MISMATCH`, `INPUT_TIME_UNCLEAR`, `PREDICTION_VALIDATION_FAILED`) have no producer and are not part of the contract. Add them with implementation, not ahead of it.

Every supported per-passenger outcome also records `basis`: the cohort key and its sample size, labelled as an exact status match or a broad-cohort fallback. A fallback estimate is a weaker claim than a cohort-specific one and a reader cannot tell them apart from the numbers alone.

### The cohort key, and who agrees on it

A cohort is `(class_code, quota_code, asof_normalized)`: the status the reservation held
**as of the moment being estimated** — `current_status` when the source recorded one,
otherwise `initial_status` in dataset rows, and the latest `StatusObservation` at or
before `prediction_at` in a served request. `railconfirm.data.preprocessing.asof_statuses()`
owns that rule, and fitting, scoring and the estimator's lookup all call it or receive
its result, so a table cannot be built from one column and queried from another.
`cohort_key()` normalises the components at both ends; status categories are expected,
not raw strings.

The artifact carries the agreement in the open: `cohort_semantics` (`asof_status_v1`) and
`features_used` (`class_code`, `quota_code`, `asof_normalized`). `load_artifact()` refuses
any artifact whose declarations differ, so the mismatch is a deployment-visible rejection
rather than a silently wrong probability. `features_used` also bounds what may be claimed
about the baseline: it reads three values, and the derived positions, queue ratio and lead
days in `FEATURE_COLUMNS` are for later estimators (ADR-0013).

## Response metadata

Every prediction should identify target definition, prediction timestamp, creation timestamp, model version, feature schema version, source/observation freshness, evidence coverage, supported/abstained state and relevant limitations. Explanation components must distinguish predictive association from causation.
