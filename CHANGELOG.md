# Changelog

Notable changes to RailConfirm Intelligence are recorded here.

The format is inspired by Keep a Changelog; dates use ISO 8601.

## [Unreleased]

Milestone A (audit and harden the implemented foundation) and the frontend rebuild. Every behaviour described as broken below was reproduced against the running code before it was changed.

### Fixed

- **A report named one target and then described a different question** (`backend/railconfirm/api/v1/predictions.py`, `backend/railconfirm/domain/prediction.py`, `frontend/src/components/prediction/PassengerOutcomeCard.tsx`). The request asks for a `target`, and `target_definition` was one hard-coded sentence — "Probability of each final-chart outcome for each passenger (CNF = …, RAC = …)" — returned for every target, so a `final_chart_cnf_or_rac` report named the merged question and captioned it with the confirmed one. The merged event's probability was not published per passenger either: a client had to add `p_cnf + p_rac` itself, and the frontend never read `target_definition` at all, labelling the card from its own `TARGET_LABELS` table. The card's fine print made the contradiction visible — "CNF and RAC … are not added together here" sat directly beneath a control that had asked for that sum, while its headline showed `p_cnf` under the heading of a target that also counts RAC. Reproduction against the fixture artifact: with `target: final_chart_cnf_or_rac` the response carried the CNF definition and `p_cnf = 0.645455`, `p_rac = 0.190909` with no field holding `0.836364` — the number the evaluation scores for that target (`EVENT_CLASSES_BY_TARGET`). `TARGET_DEFINITIONS` now lives beside the event classes in the domain, one sentence per target naming its own event, so the wording and the arithmetic cannot name different questions; the route publishes `p_target_event`, the sum of the served classes taken from the outcome itself; and the card renders each target's headline figure and its own explanation of how the classes relate. A definition that does not mention the target's event is now a test failure, a merged target must serve a figure strictly wider than `p_cnf`, and an abstaining outcome must serve none. Stored reports are not recomputed (ADR-0012), so an older one reopens with the definition it was served with and no `p_target_event`: the field defaults to `null`, which is also what an abstention publishes. No probability, calibration or artifact changes. See ADR-0036.

- **The all-CNF group score was measured against the run's event instead of CNF** (`backend/railconfirm/training/metrics.py`, `backend/railconfirm/training/report.py`). `_group_scorecard` took the run's `event_classes` and used them twice: as the label `brier_all_cnf` was scored against, and as the prevalence raised for `baseline_brier_all_cnf`. The probabilities that block scores are fixed — the independence and queue methods answer `P(all CNF)`, `P(all CNF or RAC)` and `P(at least one WL)` whatever the run asks — so under `final_chart_cnf_or_rac` the all-CNF figure was scored against "everyone confirmed or RAC", the label of the field printed beside it. On one two-passenger booking labelled `(CNF, RAC)` in a cohort at `p_cnf = 91/105`, `brier_all_cnf` read 0.4096 under the CNF target and 0.1296 under the merged one while `brier_all_cnf_or_rac` read 0.009506 under both: one number published under two names, with `brier_skill_all_cnf` comparing it against a base rate raised from the merged event's prevalence (0.0625 -> 0.2601, skill -5.5536 -> 0.50173). The two labels are now the ones the figures name (`GROUP_ALL_CNF_EVENT`, `GROUP_CNF_OR_RAC_EVENT`, read from the domain's `EVENT_CLASSES_BY_TARGET`), the baseline is the training period's confirmed share raised to the booking's size, and `_group_scorecard` no longer accepts an event argument. No key is renamed and no schema version moves: under `final_chart_cnf` every group figure is unchanged, because that target's event classes were already `("CNF",)`. ADR-0032 had recorded the target-dependence as a naming ambiguity and put it in the definitions; that treated a wrong number as a misnamed one, and the definitions are rewritten. See ADR-0035.

- **An artifact fitted under a different feature schema or status mapping was served, not refused** (`backend/railconfirm/inference/artifacts.py`, `backend/railconfirm/domain/prediction.py`, `backend/railconfirm/inference/engine.py`). An artifact declares `feature_schema_version` and `status_mapping_version`, and both were validated only for being non-empty strings — while the target, estimator, `outcome_classes`, `features_used`, `cohort_semantics`, promotion state and dataset approval are all compared against this build. The two versions that say how the cohort keys were built were the only pair left unchecked, although the loader's own docstring, ADR-0013 and `docs/research/EVALUATION_PROTOCOL.md` all state that a schema bump exists so an artifact can be *rejected rather than misread*. It is load-bearing here: the cohort key is `(class, quota, asof_normalized)`, so a different status mapping means the same raw value was counted under a different key, and schema 3.0.0 changed which status is derived (a blank `current_status` now falls back per row). Reproduced against the shared fixtures: one declared feature schema `1.0.0` and another `2.0.0` while this build derives `3.0.0`, and both loaded and served; a test wrote an artifact declaring `2.3.0` — a version this build has never had — and asserted that it was served and echoed into the prediction record, so the gap was encoded as a feature. A mismatch now refuses at metadata validation and the request abstains with `model_artifact_invalid`, naming both versions. `FEATURE_SCHEMA_VERSION` moved to `railconfirm.domain.prediction` (re-exported from `data.preprocessing`, so existing imports are unchanged) because serving needs it and importing the pandas-based feature module for one string would put pandas in the serving process — the objection ADR-0022 already upheld. `PredictionRecord.feature_schema_version` and the engine's no-artifact branch read the constant instead of the literal `"1.0.0"` they both carried, so an abstained response now reports the schema this build applies. The fixtures derive the declaration from the constants. No artifact layout, report shape or fitted artifact of this project changes. See ADR-0034.
- **A split setting that was not a number crashed instead of being refused, and two were read as something else** (`backend/railconfirm/data/preprocessing.py`). The three planners — `chronological_split`, `rolling_origin_windows`, `frozen_horizon_windows` — already refused a count that was not a positive integer, but `gap_days`, the setting that decides how much separation there must be before a block can be scored, was checked only against zero. Reproduced for all three: `gap_days="2"` raised `TypeError: '<' not supported between instances of 'str' and 'int'` out of a comparison that named neither the argument nor the caller, so a caller saw a crash where the planner meant a refusal; `gap_days=2.5` was accepted and compared against a whole-day separation as if a fraction of a day were meaningful; and `gap_days=True` — a bool, which Python makes an int — was accepted as a one-day gap by a caller who wrote it as a flag. `train_frac="0.7"` and `val_frac=None` raised the same `TypeError`, and `min_rows_per_partition=2.5` was accepted as a row floor no count can equal. Two helpers (`_require_gap_days`, `_require_positive_int`) now hold the rule, every planner calls them, and the duplicated inline checks in the two multi-window planners were replaced by them. Separately, the group-crossing refusal described a case it had not found: `chronological_split` refuses a `booking_group_id` seen on more than one journey date, and reported every such group as dates falling in more than one partition — but on the repository's own fixture for that rule both of B1's dates sit inside training, so the message pointed at the boundary while the defect was in the data. The two cases now get their own reasons: crossing the boundary is a leakage risk, two dates inside one partition is an identity problem, because one booking covers one journey. No eligible split changes, and no report field or artifact moves. See ADR-0033.
- **The group block published eight numbers with no definition, and scored a missing figure as zero** (`backend/railconfirm/training/metrics.py`, `backend/railconfirm/training/report.py`). A `GroupScorecard` is nested under a structural field, so the report's rule that every published metric has a definition never saw it: `brier_all_cnf`, `brier_all_cnf_or_rac`, `brier_at_least_one_wl`, the three `queue_brier_*` values, `baseline_brier_all_cnf` and `brier_skill_all_cnf` all appeared with no explanation — including three Brier scores of a **mathematical bound**, which the project's own rules say must never be presented as validated group behaviour. `brier_all_cnf` was also ambiguous in name: it is scored against the *target's* event classes, so it means "every passenger confirmed" for `final_chart_cnf` and "every passenger confirmed or RAC" for `final_chart_cnf_or_rac`. Separately, each of the six group probabilities was read as `indep.p_all_cnf if ... is not None else 0.0`, so a booking the group methods could not combine was scored as "certainly did not happen" and averaged into the published Brier — the same substitution ADR-0024 removed from the group methods themselves, surviving one layer up where a wrong Brier looks like a result. `GROUP_STRUCTURAL_FIELDS` and `GROUP_METRIC_KEYS` now partition `GroupScorecard` the way `STRUCTURAL_FIELDS` and `METRIC_KEYS` partition the scorecard, the report defines all eight group metrics (naming the bound, the target-dependent label, the size-dependent baseline and what skill does not compare), and a group that returns no figure is counted in `abstained_groups` instead of contributing zeros. A definition-coverage test now covers the nested block, so a new group figure cannot be published without a sentence. Fixture numbers are unchanged because every booking there combines. See ADR-0032.

- **A reliability table counted one prediction in two bands** (`backend/railconfirm/training/metrics.py`). `_bands` selected a band's members with `lower <= predicted <= upper`, so a predicted probability sitting exactly on a band edge satisfied the band below and the band above. That is ordinary rather than pathological here: the estimator is an add-one-smoothed table over five classes, so its probabilities are `(count + 1) / (n + 5)` and a fifteen-row cohort with one confirmation is exactly `0.1`. Reproduced against a fitted fixture: one scored row at `p_cnf = 0.1` was published in `[0.0, 0.1]` *and* `[0.1, 0.2]`, `sum(count)` was 2 for `scored_rows == 1`, and the event bands overlapped the same way — so a band's count, which is the only thing a reader has to judge whether its observed frequency means anything, overstated the rows it came from and averaged a row its neighbour also averaged. Bands are now half-open (`[lower, upper)`, the last including `1.0`), so they partition the scored rows; the `reliability` and `event_reliability` definitions in `METRIC_DEFINITIONS` state the rule and the invariant. No key, score, Brier value, calibration fit or artifact changes, and the fixture numbers are unaffected because their predictions do not land on an edge — which is why the existing `sum(count) == scored_rows` assertion passed. Found by reading the membership condition, not from a red test. See ADR-0031.

- **A decay report dated its drift from the wrong horizon** (`backend/railconfirm/training/decay.py`, `backend/railconfirm/training/report.py`). The frozen-artifact readout publishes the target event Brier at the first and last horizon and their difference, and it read both from the series of horizons that produced a score — while every sentence around them called them the first and last *windows*. A horizon on which every row abstained has no event Brier, which ADR-0029 established as a legitimate outcome, so on a run whose first window was silent the conclusion described a window that produced no reading and moved the start of the comparison forward without saying so; the metric definition said "last horizon minus the first horizon's", so a reader checking the number against its definition found two wrong statements agreeing. The same block had two more problems. `coverage` is defined on every horizon, so `coverage_drift` always spans horizon 0 to the final horizon while `event_brier_drift` may skip horizons at either end — an asymmetry nothing disclosed. And with two horizons, one silent, the conclusion printed `ran from 0.240000 in the window nearest the cutoff to 0.240000 in the furthest, a drift of +0.000000`: a zero difference between one number and itself, published where `MIN_HORIZONS = 2` exists precisely because a trend through one point is not a trend. `FrozenDecayResult` now publishes `scored_horizon_indices`, `first_scored_horizon` and `last_scored_horizon` (both in `summary`), the conclusion names its own endpoints and states when a silent horizon was skipped, a single scored horizon is reported as one measurement with no drift, both metric definitions state which horizons they span, the limitations list matches, and `DECAY_REPORT_SCHEMA_VERSION` moves to `1.1.0`. The arithmetic is unchanged: it is still the difference of two measured means and an ordering, not a tested trend. See ADR-0030.

- **A malformed calibration row count escaped the artifact trust boundary as `TypeError`** (`backend/railconfirm/inference/calibration.py`). `CalibrationSpec` compared `fitted_rows < 1` without checking the type first, so an artifact declaring `"fitted_rows": "120"` or `null` raised `TypeError: '<' not supported between instances of 'str' and 'int'` out of `spec_from_mapping`. The registry catches `ModelArtifactError` and reports `artifact_invalid`; a `TypeError` escapes that handler, so a hand-edited or corrupted artifact became an unhandled exception on the resolution path instead of a refusal with a reason — and the training CLI, which catches the same typed errors, printed a traceback. A fraction (`120.5`) and a boolean (`true`) were accepted outright as row counts that cannot exist. The count is now type-checked before it is compared, refusing a string, `null`, a fraction and a bool with a message naming the value and its type, matching the rule the artifact metadata already applies to `min_sample_threshold` and `laplace_alpha`. See ADR-0009 and ADR-0022.

- **A locked period that scored nothing reported itself as a crash** (`backend/railconfirm/training/calibration.py`, `backend/railconfirm/training/report.py`, `backend/railconfirm/training/__main__.py`). `CalibrationEvidence.test_effect` and `helps_on_locked_test` opened with bare `assert` statements, so a locked test partition on which every row abstained — `scored_rows == 0`, `event_brier is None`, a legitimate outcome whenever the estimator cannot reach a cohort — raised `AssertionError` from a public property. The `fit` command reaches that property *after* it has written the candidate artifact, so a fit that had completed and written its model and was about to print its summary reported itself as a failure, exited non-zero and never wrote `--report`; under `python -O` the same path returned `None - None` and raised `TypeError` instead. A missing locked reading is now `None`, `locked_test_measured` says whether the period produced an event score at all, and `helps_on_locked_test` is tri-state, so "the correction failed on the locked period" can no longer be published for a period that was never measured. The conclusion, the summary line and the terminal output all say *unknown* / *unmeasured* in that case, and `REPORT_SCHEMA_VERSION` moves to `1.1.0` because the block gained a key and one of its values may now be null. The validation side keeps refusing, but with `DatasetValidationError` naming the contradiction instead of an `AssertionError`, since a calibration that exists at all was fitted on rows that scored. The regression is covered twice: a unit test that supplies a silent locked scorecard, and a CLI test that rewrites the fixture's locked-period quota to one the cohort table never saw, so the estimator genuinely abstains and the test asserts on what `main()` printed and wrote. That rewrite also records why a changed *status* would not have worked: the lookup falls back to a broad `(class, quota, ALL)` cohort. See ADR-0029.

- **The dataset gate admitted exactly the horizon the service refuses to answer** (`backend/railconfirm/data/validator.py`, `backend/railconfirm/domain/validation.py`). Serving has always rejected a `prediction_at` on or after the journey date, because the final chart is prepared that day; the row contract rejected only `observation_date > journey_date`, so a record observed *on* its journey date was fitted with `lead_days = 0` — the one situation a date-only record cannot order against the chart and the service will not predict. The date-order check and the serving check now read one constant, `MIN_LEAD_DAYS = 1`, and such a row is refused under its own reason, `observation_on_journey_date`, counted in `same_day_observation_rows`; `date_order_violations` keeps its narrower meaning, so "the dates are backwards" and "the gap is zero" stay distinguishable in a report. The row contract is versioned (`ROW_CONTRACT_VERSION = "1.1.0"`) and every validation report now names the version it applied, so a verdict produced under the old rule cannot be read as a verdict on the new one. Existing artifacts are unaffected: they record no row-contract version and load exactly as before. A test parametrised over lead days 0, 1, 2 and 5 requires the gate's verdict and `validate_prediction_timing`'s verdict to agree at every one. The synthetic gate fixture carries a same-day row, so the reason is exercised through the validator, the training gate and the CLI, whose intake accounting is asserted from the fixture rather than from a hardcoded count. See ADR-0026 and `docs/data/DATA_CONTRACT.md`.

- **Position-band cells that could never answer a request were loaded as if they could** (`backend/railconfirm/inference/queue.py`, `backend/railconfirm/inference/artifacts.py`). `normalize_band_table` only stripped and uppercased the four parts of a band key, so a cell labelled `1-3` or `128` — the plausible misreadings of the fixed doubling cuts — loaded, counted towards `band_count` and was written back into the artifact, while `position_band` could never return that label; a key could also name a status the estimator cannot look up (`("SL", "GN", "WAITING", "1")`), which the cohort table has always refused. Neither table was cross-checked, so a band cell with no cohort row loaded too — and `estimate` resolves the cohort before it reads a band, which makes such a cell unreachable and makes a table of nothing but orphans a frequency model declaring itself position-aware. Accepted labels are now derived from `band_labels()`, with a test asserting that set equals what `position_band` returns over a long run of positions; the first three parts of a band key are validated by the cohort table's own rule (`validate_cohort_key` is now public); and `validate_band_cohorts` refuses an orphan cell in `load_tables`, in `build_artifact_document` and at `load_artifact`, so a refused load leaves the estimator unloaded rather than half-installed. The shared position fixture was itself built on orphan `ALL` cells and now declares the broad cohort its bands refine. See ADR-0025.

- **Group arithmetic clamped invalid input into a confident answer** (`backend/railconfirm/inference/group.py`, `backend/railconfirm/domain/prediction.py`). `compute_poisson_binomial_pmf` clamped each marginal with `min(1.0, max(0.0, p))` *before* testing it, so a marginal of `1.5` contributed certainty and a `NaN` did too, with nothing in the response to show the input had never been a probability. `compute_group_outcomes` compared the method name only against `"queue_dependent_comonotonic"` and sent every other string to the independence branch, so `method="queue_dependent"` — missing the suffix — returned a product of marginals labelled with a name the module does not implement; a bound and an approximation are different claims about the same booking and nothing downstream could tell them apart. `GroupOutcome` validated nothing: `p_all_cnf=0.7` beside `p_all_cnf_or_rac=0.6` was constructible, as was a group said to be 70% confirmed-or-RAC and 40% carrying at least one waitlist; the two count tables were computed from separate convolutions, so the published `P(K >= k)` need not have been the tail of the published `P(K = k)`; and both methods read marginals as `po.p_cnf or 0.0`, turning an absent number into the least probable outcome. Invalid input now raises `ProbabilityError` naming the passenger index, the implemented methods are a closed list (`GROUP_METHODS`), and `GroupOutcome` checks its own invariants on construction: all three joint figures or none, each finite and inside `[0, 1]`, `P(all CNF) <= P(all CNF or RAC)`, `P(all CNF or RAC) + P(at least one WL) <= 1`, `P(K = k)` summing to one with `P(K >= k)` its tail and `P(K >= n) = P(all CNF)`, and no figure or table carried beside an abstention. The independence branch derives its tails from its own rounded table so the two published tables reconcile by construction, and the comonotonic branch no longer clamps its sorted differences. Found by reading the arithmetic against the invariants its docstring claims; the regression tests build each case directly. See ADR-0024.

- **A calibration could correct a different event from the one its target names** (`backend/railconfirm/inference/calibration.py`, `backend/railconfirm/domain/prediction.py`). A block declaring `target: final_chart_cnf` with `event_classes: ["CNF", "RAC"]` loaded, and the same spec then produced **0.103448** on the served path and **0.058824** on the scored path — serving corrected CNF+RAC while scoring corrected CNF, so one artifact published two numbers for one claim with nothing in it to say which was meant. A `fitted_partition` of `"test"` also loaded, which is a correction tuned to the rows it is then credited with, and an unknown target such as `not_a_target` was accepted. The target → event table now lives in `railconfirm.domain.prediction` as `EVENT_CLASSES_BY_TARGET` and is read by scoring, calibration and serving alike; a block whose event classes contradict its target, an unknown target, an empty event and any partition other than `validation` are refused at construction; `apply_calibration` refuses to correct an event other than the one the spec was fitted on; and `score_rows` names the two questions before any arithmetic when a calibration's target differs from the scored one. The artifact loader settles the target against the artifact before constructing the spec, so a target switch is reported as a target switch rather than as the event-class contradiction it also causes. The merged-event test that applied a CNF-fitted spec to CNF+RAC was rewritten — it encoded the defect. See ADR-0022.

- **A model comparison could publish a contest between two different files** (`backend/railconfirm/training/compare.py`). `run_model_comparison` scored both models on the `ApprovedDataset` it was given and stamped that dataset's id and hash into the report, but never checked either model against it, or against each other; it compared partition summaries by `(name, start_date, end_date, row_count)` and nothing else, while the scoring loop walks the **baseline's** frames for both models — so two splits holding different reservations but the same dates and counts would have published the candidate's numbers from frames it never saw. `status_mapping_version`, `cohort_semantics`, `outcome_classes`, `feature_schema_version`, `laplace_alpha` and `min_sample_threshold` differences were invisible too, so a delta could blend a contract or smoothing change with the model change. Both models must now name the `(dataset_id, sha256)` pair being scored, both pairs must match, and each partition's rows are fingerprinted in stored order because pairing is by position. `pair_scores` refuses a repeated position and a partition total below the rows answered, both of which previously produced a plausible but wrong count. The verdict rule is unchanged: this only adds refusals. Found by reading the guard against the scoring loop rather than by an observed run; the regression tests build each shape directly. See ADR-0023.

- **A completed fit crashed on a Windows console.** The calibration summary line printed the before/after arrow as `→`, which `cp1252` cannot encode, so a successful run raised `UnicodeEncodeError` **after** the artifact was written — and nothing in the test suite saw it, because pytest captures its own stream rather than the console the CLI actually writes to. The training CLI and its reports now emit ASCII `->`, and tests assert that the strings they print are encodable in `cp1252`.

- **The training gate enforced the weaker of its two verdicts and passed rejected rows through** (`backend/railconfirm/training/dataset.py`, `backend/railconfirm/data/validator.py`). It tested `report.structurally_valid` — "the file parsed and one row is interpretable" — then handed on the *original frame*, so a 32-row file, a single-outcome file and a file whose dates cannot be split chronologically were all fittable, and the exact duplicates, contradictory labels, censored outcomes, unparseable dates, post-journey observations and unmappable statuses the same report counted as rejected went into the cohort counts and the scores anyway. `assess_dataset()` now returns the report **and** the frame restricted to the rows that survived every row-level check, one pass decides both so they cannot drift, and the training gate refuses any file with an eligibility finding and quotes it. The only route below the thresholds needs rows that declare `is_synthetic` *and* the explicit pipeline-test flag — passing the flag for a real file changes nothing — and the artifact records the relaxation in its own limitations. Internal index labels are reset during validation, which also removes a latent crash when a caller supplied an index with duplicate labels.

- **The baseline was fitted on one status column and queried with another** (`backend/railconfirm/training/fitter.py`, `backend/railconfirm/training/metrics.py`, `backend/railconfirm/data/preprocessing.py`). Cohort keys came from `initial_status` while evaluation and the engine looked up `current_status`, so a booking taken at `GNWL/40` and observed at `RAC 2` was counted in the waitlist cell and answered from the RAC cell: every metric described a lookup the product never performs, and every served estimate came from a different population. `asof_statuses()` is now the single definition — `current_status` when the source recorded one, `initial_status` otherwise, an unmappable value left `UNKNOWN` — and fitting, scoring and serving all use it. Verified live: two passengers booked `GNWL/40`, one observed `RAC 2`, are answered from `cohort=SL/GN/RAC n=40` (`p_cnf 0.4666667`) and `cohort=SL/GN/WL n=80` (`p_cnf 0.4823529`), matching the hand-computed smoothed cells.

- **Artifacts did not say what their keys meant, so a mismatch could not be detected** (`backend/railconfirm/inference/artifacts.py`). Metadata now declares `cohort_semantics` (`asof_status_v1`) and `features_used` (`class_code`, `quota_code`, `asof_normalized`), and `load_artifact()` refuses anything that declares otherwise — a table keyed by the booked status is rejected with an explanation instead of serving wrong-population numbers. Because the JSON layout changed, `artifact_format` becomes `railconfirm.frequency-baseline/2`; `/1` files, which declare neither field, are refused. See ADR-0013, which supersedes that one line of ADR-0009.

- **The report credited the baseline with features it never reads.** `FEATURE_COLUMNS` lists eight derived values and the report published all of them under one availability sentence, while the frequency estimator reads three. The report now separates `used_by_estimator` from `not_used_by_estimator`, names the status columns the fit actually had, and the artifact carries a limitation stating that queue positions, queue ratio and lead days are derived for later models and unused here.

- **An unrouted path did not use the documented error envelope.** `GET` on a path nothing routes to answered Starlette's `{"detail": "Not Found"}` while every other failure answers `{error, details[], request_id}` — so the contract sentence "all handled errors use one envelope" was false for the most common mistake a client can make, and a client had to special-case it. Found by watching the real browser traffic while testing the reopen route, not by a test that assumed it. A `StarletteHTTPException` handler now maps 404 to `not_found`, 405 to `invalid_input` and 5xx to `INTERNAL_ERROR` through the same envelope, and the frontend's fallback branch stays as defence against a non-conforming reply.

- **A storage rule the rest of the product does not hold rejected every real save.** The first version of the history store refused any report whose `recorded_at` preceded its `prediction_at`, reasoning that a record cannot predate the estimate it describes. The entry form defaults "estimating as of" to 24 hours ahead — a legitimate question, "will this clear by the chart?" asked about a future moment — so the browser flow produced `stored: false` with a refusal message on every attempt. The check was invented, not required: the domain already validates `prediction_at` against the journey date and against the observation times, which is where the leakage rule actually lives. Retention now runs from the save, and a test pins the future-as-of case down so the rule cannot come back.

- **A naive timestamp was silently converted before it was checked.** Normalising the stored clock to UTC happened on the same path as validating it, and `astimezone()` assumes a naive value was local time — the exact guess the store exists to refuse. The awareness check now runs before any conversion, with a test that passes a naive `recorded_at` and expects a refusal.

- **The SQLite connection was bound to the thread that opened it.** The application factory opens the store at startup, but FastAPI serves routes on other threads, so the first real request raised `SQLite objects created in a thread can only be used in that same thread`. The store now holds one explicitly shared connection behind a lock, and a test writes from six threads to prove nothing is lost — a unit test on its own thread could never have caught this.

- **Two report reads disagreed about the same number.** The write path returned the in-memory expiry with microseconds while the read path reconstructed it from second-precision text, so `retention_expires_at` differed between the response that stored a report and the response that reopened it. Stored values are now normalised through the format they will be read back in.

- **Test fixtures that reused one passenger id** produced two React children with the same key, which printed a warning in every frontend run and would have masked a real key bug. The group fixtures now use distinct ids.

- **The frontend was written against a response shape the backend never sends (`frontend/src/`).** `types.ts` declared an `observed_status` object that does not exist in `PassengerOutcomeResponse`, so the branch that rendered observed status was dead code and **no ticket status was ever displayed**; the error type expected `{error, code, detail}` instead of the documented `{error, details[], request_id}`, so every validation failure surfaced as an undifferentiated banner with no field marked; `unsupported_quota` had no entry in the abstention message map and silently fell back to the "no trained model" text, telling the user the wrong reason; `p_cancelled` was never rendered, so the probability bar summed to less than 100% while its legend claimed a complete breakdown; `(x || 0) * 100).toFixed(1)` rendered a missing estimate as a confident `0.0%`; no request had a timeout, so a hung backend left the form spinning with the submit button disabled; and `datetime-local` inputs sent naive, offset-less timestamps that the backend now rejects. Types now mirror `api/v1/schemas.py` field for field, and 81 Vitest tests — including contract fixtures copied from the backend schemas — fail if the two drift again.

- **Privacy copy claimed more than the code enforced.** "No ticket data leaves your environment" was shown regardless of where `NEXT_PUBLIC_API_URL` pointed. The page now states the actual origin and only claims "on this machine" when it is a loopback address; the data-governance page says what is true today (no third-party calls, nothing stored) instead of promising a property of the deployment.

- **Accessibility defects:** `role="status"` on static status badges announced unchanging labels as live updates; the spinner rendered its label three times; field errors had no `aria-describedby` or `aria-invalid`; passenger rows were keyed by array index, so removing a middle row reused another row's input state; the add-passenger button vanished at the limit instead of showing a disabled reason; there was no skip link and the nav had no label.

- **Grammar in count sentences** ("1 of 1 passengers have an estimate", "Group outcomes (1 passengers)"), caught by exercising the real UI rather than by rendering tests alone.

- **Status mapping integrity (`backend/railconfirm/domain/status.py`, mapping v1.1.0):** `CK` and `CKWL` were mapped to the waitlist category on an unverified guess with no reference anywhere in the repository, so a guessed family joined the waitlist population in datasets and predictions. Both now resolve to `UNKNOWN` with a note naming what must be verified before re-admission. A position token that is present but invalid (`WL/0`, `RAC 0`) was dropped without a trace; it now records a `parse_note`, so "source omitted the position" and "source gave an unusable position" are distinguishable. See `docs/model/STATUS_GLOSSARY.md`.

- **Baseline estimator evidence gate (`backend/railconfirm/inference/baseline.py`):** a frequency table could produce a confident distribution from nonsense. An unrecognised outcome key (`{"CONFIRMED": 100}`) matched no class and, because those foreign counts were summed into the denominator and the result renormalised, returned a flat 0.2 per class — a supported estimate from zero evidence. Negative and NaN counts surfaced as unhandled `ValueError`s mid-request (a 500 for a valid request), string counts raised `TypeError`, fractional counts were smoothed, and a table fitted with lowercase cohort keys silently never matched at inference, so it abstained while appearing loaded. Tables are canonicalised and validated at load before any state changes; malformed input raises `FrequencyTableValidationError`.

- **Model artifact trust boundary (`backend/railconfirm/inference/registry.py`):** `has_model()` returned True for any existing `<version>.pkl`, so a foreign or corrupt file became the active model and the engine reported that version on the response while every passenger abstained with `no_trained_model` — a broken artifact was indistinguishable from one never trained. Pickle was also the container, which executes arbitrary code on load. See ADR-0009.

- **Temporal integrity (`backend/railconfirm/domain/`):** nothing enforced a timezone anywhere. A naive `prediction_at` was accepted and echoed back; a prediction dated on or after the journey was accepted, asking for a forecast of an outcome already settled; evidence observed after `prediction_at` was used as evidence for that same timestamp, which is the leakage rule AGENTS.md and ADR-0004 state; and an observation newer than its own ingestion time was accepted. Offset-aware timestamps are now required and those cases are refused. `PredictionRecord.prediction_at` is a required field.

- **Evidence coverage and status scope (`backend/railconfirm/inference/engine.py`):** an empty passenger list reported `evidence_coverage: sufficient` because `all()` over an empty list is true; a partly supported request reported `insufficient` as though nothing worked, although the contract documents `partial`; and cancelled or censored statuses produced supported probabilities (a censored row yielded `p_cnf` 0.73) instead of an out-of-population abstention.

- **API reachability, error envelope and leakage (`backend/railconfirm/api/`):** no CORS middleware existed, so a browser on `:3000` posting to `:8000` was blocked at preflight and the frontend reported that as "could not reach the backend". FastAPI raises `RequestValidationError` for request bodies while only a `pydantic.ValidationError` handler was registered, so every `422` returned Starlette's detail array and clients could not read field paths. The `500` handler returned `str(exc)`, which can contain submitted status strings. Whitespace-only statuses became `unknown_status` abstentions that read as "unsupported" rather than "you left this empty", status strings were unbounded, and passenger lists had no server-side cap. Health reported the fallback baseline's threshold even while a promoted artifact governed predictions.

- **Dataset validation (`backend/railconfirm/data/validator.py`):** a dataset was called valid when at least one row parsed, so one good row in a 500-row file reported valid. `str(pd.NA)` renders `"<NA>"`, letting genuinely empty cells pass the required-value check; duplicates only warned and stayed in `valid_rows`; contradictory outcome labels on one reservation were undetected; dates were never parsed at all, so an observation after its own journey was accepted and `01/02/2026` would be coerced by locale; and `unknown_final_status` rows reconciled as neither valid nor rejected. Valid plus rejected now always equals total, under stable reasons.

- **Chronological splitting (`backend/railconfirm/data/preprocessing.py`):** with one or two distinct journey dates every row came back as `train` with empty validation and test frames and nothing said so; at exactly three dates `train` held six rows while `test` held none, so any metric would have scored against nothing. Splits now allocate whole dates, are independent of input row order, parse dates strictly as ISO, and return `eligible=False` with **no partitions at all** when a genuine future period cannot be held back. A `booking_group_id` spanning partitions blocks the split.

- **As-of features:** queue positions were fabricated as `0`, which reads to a model as "first in queue"; `lead_days` used `errors="coerce"` then `fillna(0)`, so a missing date asserted a same-day lead; and `.clip(lower=0)` turned a post-departure observation, which is pure leakage, into a zero-day lead. Positions are nullable, an unknown lead is null, and `extract_features` refuses a frame still carrying an outcome column.

- **CSV loading (`backend/railconfirm/data/loader.py`):** pandas accepts a short row padded with NaN, drops the surplus fields of a long row, renames a repeated column to `a.1` and a blank one to `Unnamed: 1`, all silently (confirmed against pandas 2.3.3). Header and row widths are now checked explicitly, which also keeps parsing identical across the pandas versions development and CI run.

- **CI checks were inherited from tool defaults (ADR-0010):** commit `a87afc1` passed locally and failed CI lint because `pyproject.toml` declared no Ruff rule set — local 0.16.9 enabled `DTZ001`, CI's 0.17.2 did not, so the `# noqa` markers became `RUF100` failures. `[tool.ruff.lint] select` now names the rules, Mypy is configured in `pyproject.toml`, and dev tool ranges are constrained.

- **The CI hygiene step could not fail:** `grep -r "pnr" ... | grep -v ... | head -5` inside `if ...; then` tests `head`, which exits 0 on empty input, so the "secret and private data" check warned on every commit and prevented nothing. Checks moved to `scripts/check_repository_hygiene.py`. Verified able to fail: a reintroduced broken link produced exit 1, restoring it produced exit 0.

- **Manifests asserted a clock date (`backend/railconfirm/data/manifest.py`):** `datetime.now()` meant two runs over the same file never produced the same bytes, and nothing verified a manifest against its dataset. Generation is now deterministic (`--retrieved-on` required), output follows `DATASET_MANIFEST_TEMPLATE.yaml` section-for-section — previously only `sha256` matched by name — and `verify_manifest` re-hashes and **recounts** rows and duplicates instead of trusting what the file claims.

- **A passenger's target-event probability is served beside the classes it sums** (`backend/railconfirm/domain/prediction.py`, `backend/railconfirm/api/v1/schemas.py`, `frontend/src/lib/types.ts`). `PassengerOutcome.probability_of(classes)` sums the classes an event covers from the one distribution the report published, and refuses an unknown class name instead of skipping it — a typo would otherwise shrink a probability of confirmed-or-RAC into a probability of RAC, silently. The same call is what the response field `p_target_event` carries, so the browser renders the figure the evaluation scores rather than re-deriving it with its own rounding, and `None`/`null` on abstention because an absent estimate is not zero. - **Paired model comparison, judged on the locked period only (`python -m railconfirm.training compare`, ADR-0021).** Roadmap Phase 4's exit gate has been "candidate evaluated on locked later journeys and compared with baseline", and the repository could fit two models and score each on its own split without being able to answer it. `run_model_comparison()` refuses anything that would not be a comparison: different split partitions, different targets, the same estimator on both sides, or two different prevalence baselines. Both models are then scored on the same rows against one baseline taken from the shared training window, and rows are paired by **partition position** — the key that survives the two models abstaining on different rows, which an identity key would silently drop or duplicate.
  - The verdict requires four things at once on the **locked period**: distribution Brier improved, event Brier improved, coverage not worse, strictly more paired wins than losses. Anything else is `baseline`, each failing condition printed at its own numbers; a locked period with no rows both models answered is `undetermined`, which is not a pass. There is no flag to choose a different deciding window, for the reason ADR-0018 gives for its cutoff.
  - Rows only one model answered are counted in `only_baseline_scored` / `only_candidate_scored` and never as wins; an abstention is a coverage fact (ADR-0011), and a candidate that refuses the hard rows is disqualified by the coverage condition rather than rewarded for it. Pairing uses the target event's squared error — the number a passenger is handed — while the distribution Brier must improve too, so a win cannot be manufactured inside the event's complement.
  - `score_partition(..., pre_scored=…)` lets the comparison reuse the rows it already walked, so the published aggregates and the paired counts cannot drift apart while both look right. (The first draft named the parameter `scored`, which already means "count of scored rows" inside that function; the type checker caught the collision.)
  - Live on labelled synthetic fixtures built to have known answers: on a fixture whose labels depend on queue position the candidate **lost validation** (Brier delta `+0.070624`) and **won the locked period** (`-0.038673` distribution, `-0.028502` event, 62 wins against 18 losses) → `Verdict: candidate`; on a position-blind fixture the same code reported `Verdict: baseline` with three named blocks (locked distribution `+0.172314`, event `+0.077057`, 32 wins against 48 losses). Both fixtures are made up; neither is evidence about railways, and promotion stays a human act. 29 new tests.

- **A second estimator: cohort cells split by the as-of queue position (`backend/railconfirm/inference/queue.py`, ADR-0020).** `FEATURE_COLUMNS` has derived `asof_position` since schema 3.0.0 and the served estimator read three of the eight columns, so the report honestly said the position was unused. A flat cohort rate answers a passenger first in the waitlist and one two hundred deep with the same number — an average over a queue rather than a model of one — so `cohort_position_baseline` now keeps the same cohort key `(class_code, quota_code, asof_normalized)` and splits each cohort by fixed doubling bands (`1, 2-3, 4-7, 8-15, 16-31, 32-63, 64-127, 128+`). Fixed widths, never training quantiles: cuts that move with the file make two artifacts non-comparable and let a served probability depend on which rows happened to be in the fitting period.
  - The position is read from the same parsed as-of status that supplies the cohort key — in the fitter, in `score_rows` and in the engine — so fitting, scoring and serving consult one field. That is ADR-0013's rule applied one column wider.
  - A band below `min_band_rows` (default 2, recorded on the artifact because it changes the served number) does not answer: the cohort rate does, and `basis` says `band=8-15 n=1 below the 2-row band floor, cohort rate used`. A status with no position token is unknown, not first in the queue: `as-of queue position unavailable`. One row cannot express a rate; it expresses one outcome.
  - New artifact format `railconfirm.cohort-position-baseline/1` with band cells keyed `CLASS|QUOTA|STATUS|BAND`. Frequency artifacts stay `/2` and mean what they meant. `load_artifact()` refuses every direction of disagreement — format against estimator, unknown estimator, `features_used` that does not match the declared estimator, band cells on a frequency artifact, a position artifact with no band cells, three-part band keys, malformed counts — and `write_artifact()` refuses to create the same mismatches. Serving builds through `LoadedArtifact.estimator()`, offline evaluation through `estimator_for(provenance)`; nothing may assemble an estimator from a cohort table by hand.
  - Trust gates are unchanged and apply to either model: provenance decides whether a table may estimate, a synthetic or unapproved artifact still abstains, `apply_calibration` still moves the event mass, group arithmetic still reads the passengers it is given, and a fitted artifact is still a candidate.
  - On the labelled synthetic fixture the position model **loses**: locked-test event Brier `0.275914` against the flat model's `0.239960`, and frozen decay `0.246575 → 0.275914` (+0.029339, 0 of 2 horizons beating the base rate) against the flat model's `-0.000125` and 1 of 2. The fixture's labels are deliberately independent of queue position, so that is the expected answer: the mechanism works, and whether the position model deserves promotion is ADR-0021's question to ask of real data. 94 new tests (52 estimator, 21 artifact and registry, 21 pipeline and CLI).

- **Subgroup calibration measured per segment (`backend/railconfirm/training/metrics.py`, `backend/railconfirm/training/report.py`, ADR-0019).** A single logistic correction moves every row's log-odds by the same rule, so two cohorts sitting on opposite sides of the population mean can average out to a well-calibrated headline while each one stays wrong — and reliability bands cannot show it, because they pool classes by construction. Every `Scorecard` now publishes, for each slice it already segments by (`class_code`, `quota_code`, `asof_status`, `initial_status`): `mean_predicted`, `observed_rate`, `gap = observed - predicted` and the row count.
  - The numbers are the **served** ones: `mean_predicted` is the event mass after `apply_calibration` when the artifact carries a layer, because a gap measured beside the probability nobody was handed describes a different product.
  - Nothing is fitted per cohort, and the report says so: the gaps are one population-wide slope's residual error, not evidence that the correction holds inside a class. A per-segment slope on cohorts counted in the tens would be noise, and a probability whose provenance depends on the passenger's class is not a model.
  - The claim carries a floor. `gap` is published for every segment, but a slice under the scorecard's `min_segment_rows` (default 25) is flagged `low_sample` and no conclusion may rest on it; when no segment clears the floor, the report states that subgroup calibration cannot be claimed in either direction instead of quoting a thin cohort to fill the line.
  - Abstained rows contribute to no segment, so per-dimension row counts sum to `scored_rows` — a test asserts that accounting, because a silent mismatch would quietly reweight the population toward the easy rows.
  - The repository's own rule that every published scorecard number must have a definition caught the new field the moment it was added; the fit, rolling-origin and decay reports inherit the measurement unchanged. On the labelled synthetic fixture (`fit --report`, exit 0) validation shows `asof_status=WL` at predicted 0.388169 against observed 0.400000 over 40 rows (gap +0.011831, informative) next to `class_code=SL` at 23 rows (+0.005887) and `class_code=3A` at 17 rows (+0.019873), both flagged `low_sample` — the widest gap is the thin one, which is exactly why the floor exists. 22 new tests; no railway claim, and nothing in the serving path changed.

- **Frozen-artifact decay (`python -m railconfirm.training decay`, ADR-0018).** Rolling origins refit at every cutoff, which measures the fitting procedure; a promoted artifact faces the other question — one table, judged further and further from the period it was counted from. `frozen_horizon_windows()` plans whole-date horizons after the cutoff, where the cutoff is the **artifact's own `trained_to`** and never a caller's flag, because a chosen cutoff lets the fitted dates be reported as evidence about the model that saw them. `run_frozen_decay()` applies the artifact's cohorts, `min_sample_threshold`, `laplace_alpha` and calibration block unchanged to every horizon through the same `build_estimator()` gate the registry loads through, against **one frozen prevalence baseline** computed from the fittable rows at or before the cutoff — a baseline recomputed per horizon would drift toward the answer it is judging. The run refuses below `MIN_HORIZONS = 2` usable horizons rather than drawing a trend through one point, refuses when any `booking_group_id` spans the cutoff, refuses an artifact whose declared cohort rule or feature list differs from what this build serves, and counts horizons that abstained everywhere separately from horizons that lost to the baseline. What it publishes is drift: first-horizon and last-horizon values, their difference, and the spread, never a mean that would hide the ordering. On the labelled synthetic fixture the estimator a single cutoff reports as event Brier `0.239487` against a `0.24` base rate scores `0.243482 → 0.240300 → 0.239411` across three two-date horizons and beats the frozen baseline in **one of three**; the calibrated artifact's horizons reproduce `fit --calibrate`'s own validation and locked-test numbers exactly (`0.239898`, `0.239487`), which is parity, not performance. Reports keep `--generated-on` byte-reproducibility and add definitions for `prevalence`, `event_brier_drift` and `coverage_drift`. 74 new tests (39 planner, 35 evaluation/report/CLI) cover the windows, the refusals, the frozen-baseline behaviour, the calibration carry-through, the derived conclusions and a cp1252 encodability guard on everything printed.

- **Logistic calibration fitted on validation and measured on the locked test (`backend/railconfirm/training/calibration.py`, `backend/railconfirm/inference/calibration.py`, ADR-0017).**
  - `fit --calibrate` fits a slope and intercept for the target event's log-odds by Newton–Raphson on the **validation** partition only. It needs `--calibrate-min-rows` (default 50) scored rows whose predicted event probability lies strictly inside `(0, 1)`, and it refuses rather than degrades when the window cannot support a slope: one label, one repeated prediction, a prediction outside `[0, 1]` (a scoring bug, not a data problem), a singular Hessian from perfectly separable evidence where the maximum-likelihood slope runs away, non-convergence inside 100 iterations, or a **negative** slope, which would mean the evidence is anti-correlated with the outcome.
  - The layer is embedded only when it **strictly reduces validation event Brier**. The locked test is scored with and without it whatever the verdict, and `fit` prints both: `validation event Brier X -> Y; locked test A -> B (helped / did not help)`. An improvement in-sample that costs out-of-sample is therefore visible on the same screen that wrote the artifact.
  - `apply_calibration` is the single correction path: it rescales the target event's mass and redistributes the remainder proportionally so every distribution still sums to 1, leaves abstentions untouched (there is no probability to move, and rewriting the reason a row refused would hide it), and adds the calibration identity to the evidence basis. The evaluator scores with it and the engine serves with it, so the measured number and the served number are the same arithmetic.
  - Artifact metadata now carries `calibrated` and the `calibration` block, and `load_artifact()` refuses the two disagreeing in either direction — a `calibrated: true` claim with no block, and a block that declares itself unused. Each scorecard records `calibration_applied`, reliability bands are computed on the corrected probabilities, and both report and artifact state that the correction was measured across the population, **not** within a cohort subgroup.
  - On the labelled synthetic fixture the correction moves validation event Brier `0.240085 -> 0.239898` and the locked test `0.239960 -> 0.239487`; served `p_cnf` for one `SL/GN/WL` passenger changes `0.385416667 -> 0.391304348`. That is evidence the mechanism runs and is measured, not a railway calibration result — no approved dataset exists, so nothing here has been fitted on real outcomes. 68 tests cover the fitter's refusals, the redistribution arithmetic, the artifact-claim enforcement, and the evaluator/engine parity.

- **Rolling-origin evaluation (`python -m railconfirm.training origins`, ADR-0014).** `rolling_origin_windows()` plans whole-date expanding cutoffs — `min_train_dates` dates to start, the next `horizon_dates` scored, advancing by `step_dates`, with an optional calendar gap — and refuses to produce any window when the calendar supports fewer than two cutoffs, because one measurement under a plural name is how a trend gets invented. `run_rolling_origins()` refits the cohort table **and** its prevalence baseline from each origin's own past, so no cutoff is scored against a baseline fitted on the answer. The report prints `refit-per-origin, score-the-next-horizon`, counts origins that produced a score separately from origins that abstained everywhere, states the Brier and coverage ranges instead of averaging them away, and fixes the limitations that overlapping windows are not independent evaluations and that no multiplicity correction is applied. Reports stay byte-reproducible with `--generated-on`. 44 tests cover the planner, the arithmetic against hand-checked cells, the refusal paths and the wording.

Also raises the artifact format to `/2`, which ADR-0009's status line now points at.

- **JSON model artifacts with two-gate promotion (`inference/artifacts.py`, ADR-0009):** an artifact declares its format, version, target, feature-schema and status-mapping versions, outcome class order, dataset id and SHA-256, approval status, fitting window and promotion state. Serving requires both `RAILCONFIRM_ACTIVE_MODEL_VERSION` naming the file and metadata declaring `approved_for_local_use`, so a file appearing in `models/` activates nothing. Reads are size-bounded, version names are path-safe, and pickle is not an accepted format.

- **Abstention reasons that name the closed gate:** `no_approved_data` ("no evidence base exists") and `model_artifact_invalid` ("configured artifact rejected") join `no_trained_model`, because those three call for different unfinished work. Documented in `docs/technical/INFERENCE_AND_GROUP_PROBABILITIES.md`.

- **Estimator provenance:** a frequency table can only be installed with `FrequencyTableProvenance` (dataset id, SHA-256, source reference, approval status, synthetic flag, fitting window). Only a real, explicitly approved dataset yields estimates — a passing quality check is not a licensing decision, and synthetic fixtures prove arithmetic, not railway behaviour.

- **Evidence basis on every estimate:** `PassengerOutcome.basis` records the matched cohort and its sample size and states whether a broad-cohort fallback was used; exposed as `basis` in the API response. A fallback is a weaker claim than a cohort match and the numbers alone do not show which ran.

- **API surface:** CORS with an explicit origin allowlist, a `413` body-size limit, `X-Request-ID` on every response, privacy-aware access logging (method/path/status/duration only), engine dependency injection replacing the module-level singleton, `target` selection on the manual route, and `registry_status`/`model_available` on prediction and health responses.

- **Dataset intake command line:** `python -m railconfirm.data validate|manifest|verify` with documented exit codes and a `--json` report form.

- **Approval cannot be manufactured by a script:** `status: approved` requires `decision.decision: approved` with `reviewed_by`, `reviewed_on` and a rationale, plus an approved licence review permitting model training; `licence_review_status: approved` is refused while training use is `unknown`; `privacy.contains_raw_pnr: permitted` is refused outright. The status vocabulary is closed, so `approved_for_training`, `metadata_only` and `synthetic_test_only` no longer parse.

- `EligibilityThresholds` makes the intake minimums explicit and configurable; `SplitResult` publishes per-partition row counts, distinct dates, distinct bookings and boundaries; `FEATURE_SCHEMA_VERSION`/`FEATURE_COLUMNS` are now the shared feature definition training and inference must agree on.

- **Baseline training pipeline (`backend/railconfirm/training/`, ADR-0011):** `dataset.py` is the only way training obtains data — the manifest must verify against the file it describes (hash, size, recounted rows), a named reviewer must have recorded an `approved` decision with a rationale, `licence_review_status` must be approved **and** `allowed_uses.model_training` must be `permitted`, and rows declaring `is_synthetic` are refused unless the caller opts in for pipeline testing, which marks the resulting artifact unservable. `fitter.py` counts cohorts from the training partition only, refuses an ineligible split, validates the fitted table through the same `normalize_frequency_table` gate inference uses, records the training window and exclusion counts, and always writes `promotion: "candidate"` — fitting activates nothing.

- **Probability evaluation (`training/metrics.py`):** multiclass Brier and log loss for held-out rows, each compared with a prevalence baseline computed from the **training** period, plus `brier_skill`, coverage, abstention counts, per-class reliability bands with counts, and per-segment scores that carry their row counts and a `low_sample` flag. Abstained rows are excluded from the scores instead of being counted as wrong. Scoring uses the same `HistoricalFrequencyBaseline` object inference serves from, so a metric cannot describe a code path the product does not run.

- **The target's own event is scored, not just the distribution (`TARGET_EVENTS`):** `final_chart_cnf` scores the confirmed mass against a 0/1 label and `final_chart_cnf_or_rac` scores confirmed-plus-RAC, each with its own binary Brier, log loss, prevalence baseline, skill and reliability bands. The report prints a verdict for both and adds an explicit line when they disagree about beating the base rate — which they do on the synthetic fixture (distribution 0.501038 against a 0.500000 baseline, CNF event 0.232664 against 0.250000), so quoting one number would have hidden the other result.

- **Reproducible evaluation reports (`training/report.py`):** deterministic JSON — `--generated-on` is required and nothing reads the clock — publishing split boundaries, rows used and excluded per reason, the feature list with its availability statement, the dataset hash and approval state, metric definitions, segment counts and a limitations block that states when no calibration was fitted. Conclusions are derived from the measured verdicts rather than hand-written, `METRIC_KEYS` is derived from the scorecard's own fields, and a test fails if a published number lacks a definition or a definition describes nothing published.

- **Training command line:** `python -m railconfirm.training fit|evaluate` with `--target` restricted to targets that have a defined event, target agreement checked against the artifact's declared target, and `Refused: …` on exit 1 for blocked data, ineligible splits and rejected artifacts instead of a traceback.

- **`FrequencyTableProvenance.evaluation_only`:** a memory-only flag that lets synthetic cohorts be scored so the metrics code is actually exercised. It is not a field of `ModelArtifactMetadata`, so no stored artifact can carry it, and it does not override the approval requirement — tests assert both.

- **Opt-in local prediction history (`backend/railconfirm/storage/`, ADR-0012).** A report can now be kept and reopened, which is what `/prediction/[id]` — documented in the frontend guide since the start and previously decoration — needed. Storage requires two independent switches: `RAILCONFIRM_PERSIST_PREDICTIONS` on the server (default **false**) and `"persist": true` on the request. The response carries `stored`, `report_url` and `retention_expires_at`, so "did my report get kept?" is answered by the server rather than assumed from the request; a save the store refused still delivers the estimate and puts the reason in `limitations`. `GET /v1/predictions/{prediction_id}` returns the stored response unchanged — nothing is recomputed, because a reopened report is evidence about what was said then, with the model version it came with. Retention is enforced twice over: an expired id stops resolving before a purge ever runs, and `prediction_retention_days` refuses a value below 1. `DENIED_KEYS` and a PNR-shaped-value scan run at the write, so a future field cannot start storing a passenger name or a PNR by oversight, and a 10-digit id on the reopen route is refused with a message saying reports are reopened by the id the server returned. SQLite in one Git-ignored file, no new dependency, no server; `data/storage/` and `*.sqlite3*` are ignored so a history file cannot be committed.

- **`/prediction/[id]` in the frontend** renders the kept report with a banner saying it is "the report as it was served" and when that copy stops being retrievable, and separates the three reasons a report can be unavailable — never stored, aged out, this server keeps no history — because they call for different actions. The entry form's new "keep this report" control states that the response says whether it was actually kept.

- **`GET /v1/health` reports `prediction_history`** (`enabled`, `retention_days`, `stored_reports`, empty when disabled), so an interface can stop offering to save where saving is impossible, and an operator can see the state without opening the file.

- **Candidate dataset review (`docs/data/CANDIDATE_DATASET_REVIEW.md`):** the search for a trainable dataset is now recorded with evidence instead of being described as a gap. Four candidates were inspected on 2026-10-23 — a Kaggle "Indian Railway Ticket Confirmation" set whose own page says it is *"synthetically generated and does not represent real data"* (MIT, rejected), an IRCTC-scraped schedule/fare/availability set with no per-reservation chart label (Apache 2.0, rejected for training), a stations/trains/schedules metadata set credited to DataMeet (Kaggle lists `CC0: Public Domain`, under review for reference use only), and its origin repository `datameet/railways`, which cites CC0 in prose but **has no licence file**, so the grant is unconfirmed. `data.gov.in` returned HTTP 403 to an unauthenticated automated fetch, so its holdings were not read. No file was downloaded or ingested. The finding is specific: none of these carries both a reservation's booked status and its verified final-chart outcome under training permission, which is what the abstention behaviour is waiting on. `docs/data/SOURCE_REGISTER.md` records each verdict and `docs/PROJECT_STATUS.md` states the blocker in those terms.

- **History listing and per-report deletion (`backend/railconfirm/storage/`, ADR-0015, ADR-0012).** `GET /v1/predictions` lists kept reports by id, target, model version, and retention clocks with no payload content, and answers 404 with `history_disabled` rather than an empty list when the store is off, so `nothing kept` and `storage disabled` are distinct states for a client to act on. `DELETE /v1/predictions/{id}` removes the row immediately; absent, expired and already-deleted ids all return the same 404 body. `PRAGMA secure_delete = ON` zeroes freed pages (WAL side-files and filesystem snapshots are outside this scope, documented). The frontend history page (`/history`) shows kept reports newest-first with a two-step deletion flow: the first click shows Confirm with a Keep it escape, the second issues the DELETE; a refused or network-failed delete leaves the row listed and says why.

- **Dependent group outcomes, Poisson-binomial distribution, queue-clearing bounds, and group evaluation (`backend/railconfirm/inference/group.py`, `backend/railconfirm/training/metrics.py`, ADR-0016, ADR-0003).**
  - Added exact dynamic programming Poisson-binomial distribution convolution (`compute_poisson_binomial_pmf`) computing exact PMF ($P(K = k)$) and tail probabilities ($P(K \ge k)$) for multi-passenger bookings under the independence baseline.
  - Implemented sequential queue-clearing model (`compute_queue_dependent_bounds`) capturing the Fréchet-Hoeffding comonotonic upper bound ($P_{\text{all CNF}} = \min_i p_i$, $P(K \ge k) = p_{(k)}$) reflecting the positive correlation inherent in Indian Railways FIFO queue clearance.
  - Added multi-passenger group outcome evaluation in `score_partition()`: groups partitions by `booking_group_id`, computes Brier scores for both the independence baseline and the queue comonotonic bound against observed group outcomes (`all_cnf`, `all_cnf_or_rac`, `at_least_one_wl`), compares against group prevalence baselines, and generates `GroupScorecard`.
  - Exposed `p_at_least_k_cnf` and `p_exactly_k_cnf` on `GroupOutcomeResponse` schema and Next.js frontend, rendering confirmed berth distributions for multi-passenger groups.

### Changed

- **A rolling-origin run published one aggregate, and it was the flattering one** (`backend/railconfirm/training/origins.py`, `backend/railconfirm/training/report.py`). Each origin's score is a mean over the rows that origin scored, so the published mean of those means gave a two-row horizon exactly the weight of a two-thousand-row one. That figure answers "how did the fitting procedure do per cutoff" and reads as if it answered "what did a passenger get per prediction"; on a plan with uneven horizons — the normal case, because the last horizon in a file is often a partial date block — the two can land on opposite sides of the same baseline. Nine small horizons that scored well and one large one that scored badly produced a mean that beat the base rate while the error over the rows actually served lost to it. `RollingOriginResult` now publishes `pooled_brier`, `pooled_baseline_brier`, `pooled_event_brier` and `pooled_event_baseline_brier` weighted by scored rows, beside the mean over origins it already had, plus `scored_rows_spread` and two verdicts — `distribution_agreement` and `event_agreement` — that say whether the two aggregations reach the same conclusion against their own baselines (`agree`, `disagree`, or `undetermined` when nothing was scored). A disagreement is a conclusion in the report, printing both pairs of numbers and stating that which figure a reader quotes decides the verdict, so neither is presented as *the* result; an agreement names the pooled figure as the one a statement about served predictions should rest on. Uneven horizons add a limitation saying the two figures are not interchangeable, and the terminal output prints the range instead of warning on every balanced run. Both statistics are defined in the report's own `metric_definitions` block, and `ORIGIN_REPORT_SCHEMA_VERSION` rises to `1.1.0` because the aggregate gained keys — no existing key changed meaning. Seven regression tests cover the weighting, the abstaining origin that must not act as a zero, a constructed plan where the two aggregations disagree, and the balanced plan where they must coincide. See ADR-0028.
